## 1. Postal Code Routing — Out-Of-Box Kyu Kaam Nahi Karta

### Original Requirement

**8 countries ke zip codes, 30 regions.**

### Lead Ko Sahi Region Tak Kaise Bhejein

**Lead aayi → 8 countries mein se kisi ek se**

**Postal Code se route karna hai → 30 regions mein se ek**

### Kaunsa Mechanism?

#### Success Path

**Custom Territory Object + Apex**

Territory definition mein:

- ZIP / Postal Code
- State
- Country
- Region

define kiya ja sakta hai.

#### Before Insert Apex

Lead ke:

- Country
- State
- ZIP / Postal Code

ko dekh kar appropriate territory stamp karo.

#### Lead Assignment Rules = 30 Lines

```text
Region 1 → Queue 1
Region 2 → Queue 2
Region 3 → Queue 3
...
Region 30 → Queue 30
```

#### Account Par Bhi Territory

Lead conversion ke time territory information ko Account par bhi carry kiya ja sakta hai.

Person Account scenario mein bhi appropriate territory information maintain ki ja sakti hai, jisse baad mein Case Management mein region use ho sake.

## 2. Failure — Seedhe Lead Assignment Rules

### Original Approach

**Har ZIP code ke liye ek line.**

```text
ZIP Code → Region
ZIP Code → Region
ZIP Code → Region
...
Thousands of ZIP Codes
```

### Problem

- Hazaaron Rule Entries
- Maintenance difficult
- New ZIP codes add/update karna difficult
- Multiple countries aur regions ke saath mapping complex ho sakti hai
- Large geographic mapping unmaintainable ho sakti hai

**Original script reference:** Limit lagbhag **2,000 entries** batayi gayi hai.

### 2026 Update

Sirf "2,000 entries limit" ko architecture ka sole reason mat banao.

2026 mein stronger architectural answer:

> **"I would not model thousands of postal-code mappings directly inside Lead Assignment Rules. I would externalize the geographic mapping into configurable data and use automation/code to resolve the region."**

Conceptually:

```text
Postal Code Mapping
        ↓
Country / State / ZIP
        ↓
Territory / Region
        ↓
Lead Region
        ↓
Queue / Owner
```

Is approach se geographic mapping ko configuration/data ke form mein maintain kiya ja sakta hai, instead of repeatedly hard-coding postal-code logic.

## 3. Enterprise Territory Management Kyu Nahi

### Original Point

Enterprise Territory Management bhi "ye code, wo code, wo code" wali lines ka set hi hai — aur **Leads out-of-the-box territory management mein support nahi hote**.

Isliye custom object + Apex ko practical approach maana gaya.

### 2026 Salesforce Context

Core conclusion ab bhi important hai:

**Enterprise Territory Management (ETM) ko direct Lead postal-code routing engine ke roop mein treat nahi karna chahiye.**

Agar requirement hai:

> Lead ke Country + State + Postal Code ke basis par Lead ko 30 geographic regions mein automatically route karna.

Toh Lead routing ko separate design karna better hai.

### Lekin ETM Ko Completely Reject Nahi Karna Chahiye
